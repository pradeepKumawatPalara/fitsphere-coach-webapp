# ADR-012 · CSV export: browser for selected rows, server for full export

| | |
|---|---|
| **Status** | ✅ Accepted (decision made by the business owner; recorded retroactively as an ADR) |
| **Log entry** | D-12 in `docs/DECISIONS.md` |
| **Date** | Nov 2026 |
| **Owner / approver** | Business owner *(name and approval date to be filled in)* |
| **Scope** | Export of client data to CSV from the Clients list |
| **Risk tier** | High (bulk export of personal data) |

## Context

Coaches pick the fields and export either some clients (selected rows or the current page) or the whole client list. Bulk export of personal data is a privacy and security risk, must be rate-limited, and the coding standard requires an audit log for CSV export (OWASP A09). Large exports can time out (OWASP A10).

## Options considered

Scores are 1–5 per criterion (5 = best) using the framework weights. **Security, privacy and legal are pass/fail first.** Scores are the architect's proposal for owner review.

| Criterion (weight) | A. Hybrid: browser for selected rows/page; API for "export all" | B. Everything in the browser | C. Everything through the API (including selected rows) |
|---|---|---|---|
| Security / privacy gate | Pass, if browser exports are also audited (see Open points) | At risk: needs all data in the browser, no server record | Pass |
| Security (20%) | 3 | 2 | 5 |
| Maintainability (20%) | 3 | 4 | 4 |
| Reliability (15%) | 4 | 2 | 4 |
| Performance (15%) | 4 | 2 | 3 |
| Scalability (10%) | 4 | 1 | 4 |
| Cost (10%) | 4 | 5 | 3 |
| Integration (10%) | 4 | 3 | 4 |
| **Weighted score** | **3.60** | **2.70** | **3.95** |

**Architect note:** the score favours option C, mainly because a browser-side export leaves no server-side audit record and cannot be rate-limited. The owner's decision for A stands, with the conditions below. If the audit and rate-limit gap cannot be closed cheaply, move to C.

## Decision

**Option A.** The coach chooses the fields. Selected rows or the current page are exported in the browser. "Export all clients" is generated by the API and streamed back (a background job for big gyms, rate-limited).

## Why

- Instant and cheap for small exports; no server work for a few rows.
- Server handles the large, risky case with limits and job status.

## Rejected

- **B. All in the browser:** would require loading the whole list into the browser; times out on big gyms.
- **C. All via the API:** safest and best audited, but adds server load for tiny exports. Remains the fallback (see the note above).

## Consequences

- The API export endpoint is rate-limited, uses idempotency keys, and runs as a background job with status polling for large gyms (see `docs/best-practices/01-coding-best-practices.md`).
- Export of a very large list handles timeouts and partial failures explicitly.
- CSV correctness: column order, escaping of commas and quotes, special characters in names (unit-tested; see `docs/best-practices/02-testing-and-unit-testing.md`).
- Guard against CSV formula injection (cells starting with `=`, `+`, `-`, `@`).
- Only the fields the coach is allowed to see are exportable; permission is enforced by the API.

## Related decisions

ADR-004, ADR-005, ADR-011, ADR-014, ADR-020.

## Open points

- **Audit trail for browser-side exports:** for example, the web app calls an audit endpoint recording who exported which fields and how many rows before the file is generated.
- Which fields are exportable, and whether any (for example date of birth, phone, health data) need admin-only access.
- Threshold between "browser export" and "must use the server" (for example a maximum row count).
